# Optional Hyper-V backend

When you need a separate operating system and filesystem, a dedicated Hyper-V Windows VM remains available. An existing `version: 1` configuration automatically selects `hyperv`; no migration is needed. The default backend when nothing is configured is the native Child Session — see the [README](../README.md).

## Prerequisites

Host: Windows with Hyper-V and the Hyper-V PowerShell module; the Claude Code process needs Hyper-V management and PowerShell Direct permission; Node.js 22+, Windows PowerShell 5.1, and the system RDP ActiveX control.

Guest:

- A dedicated, properly licensed Windows VM with RDP hosting — not a daily-work VM.
- Node.js 22+ and cua-driver 0.34.0+ installed inside the guest.
- RDP enabled with NLA required, and network access allowed from the host. The plugin does not set these policies.
- The server certificate is trusted by the host and matches the RDP address; self-signed or name-mismatch errors are never ignored.
- A dedicated password-protected guest administrator account for PowerShell Direct and RDP; interactive operations never auto-elevate UAC.
- A working Explorer, a usable Win+R dialog, no lock screen / logon banner / blocking dialogs, and a US English keyboard layout at startup.
- The dedicated account is not shared with other controllers or users.

## Preparing the VM

Skip creation if you already have a dedicated VM. If you have an offline, installed Generation 2 bootable VHDX, preview first:

```powershell
.\scripts\New-CuaRdpVm.ps1 -Name "CuaDesktop" -BaseVhdPath "D:\Images\prepared-windows.vhdx" -VmDirectory "D:\VMs\CuaDesktop" -SwitchName "Default Switch" -WhatIf
```

Remove `-WhatIf` to create after reviewing. It uses a differencing disk, never modifies the parent disk, never overwrites an existing target, and does not start the VM. The parent disk must stay unchanged while in use. Afterwards the user starts the VM and completes Windows, account, network, RDP, certificate and runtime setup.

## Initialization

In an interactive PowerShell as the same host user with Hyper-V management permission:

```powershell
.\scripts\Initialize-CuaRdp.ps1 -VmName "CuaDesktop" -RdpAddress "cua-desktop.example.internal" -GuestDriverPath "C:\Users\Automation\AppData\Local\Programs\Cua\cua-driver\bin\cua-driver.exe"
```

The domain name must resolve only to the selected VM's IPv4; targets containing IPv6, host addresses, localhost, or another machine's address are rejected. The script prompts interactively for guest credentials; the password never enters chat, command lines or JSON. Credentials are saved with the current host user's Windows DPAPI via `Export-Clixml`, and the directory ACL is limited to that user, Administrators and SYSTEM.

Optional parameters: `-GuestNodePath`, `-GuestRoot`, `-ConfigPath`, `-RdpPort`, `-Width`, `-Height`, `-AutoStartVm`. `-WhatIf` previews; an existing installation is refused by default, and an explicit `-Force` backs up and replaces it — but is still refused while uncleaned run directories exist.

The script only installs the plugin's agent files and configuration; it does not enable RDP, change firewall rules, import certificates, or create scheduled tasks. To use a different configuration path, set `CUA_RDP_CONFIG` before starting Claude Code.

Example (generated by the initialization script):

```json
{
  "version": 1,
  "backend": "hyperv",
  "vmId": "11111111-1111-1111-1111-111111111111",
  "guestMachineGuid": "22222222-2222-2222-2222-222222222222",
  "credentialPath": "C:\\Users\\You\\AppData\\Local\\CuaRdp\\credential.clixml",
  "guestRoot": "C:\\ProgramData\\CuaRdp",
  "autoStartVm": false,
  "rdp": { "address": "cua-desktop.example.internal", "port": 3389, "width": 1600, "height": 900 }
}
```

Check and load:

```powershell
npm run doctor
claude --plugin-dir "E:\Repository\cua-rdp"
```

Tools, skills and error handling are identical to the Child Session backend. `desktop_start` results report `backend: hyperv`.

## Lifecycle and limits

The target is verified through the VM GUID, a MachineGuid different from the host, the guest SID, and the active RDP SessionId. The RDP control is hosted on a host-side private Win32 desktop; authentication and redirection checks stay strict. Requests reach the guest loopback proxy through PowerShell Direct — the proxy port is never exposed to the network.

Large responses are capped at 64 MiB and transferred in 256 KiB chunks; the original action executes exactly once, and the lease is renewed separately during long transfers. Requests are capped at 2 MiB, and the host waits at most 360 seconds for a transfer.

Stopping closes this controller's keeper first, then confirms the agent exited; on failure the VM-exclusive lock and files are retained. Nothing is logged off, shut down, or closed. After the main process exits, the Job Object closes the keeper and the guest agent exits via its stop marker or a lease of at most 180 seconds.

A VM does not isolate networks, website accounts, or the consequences of the task itself. Sending mail, purchasing, deleting and similar actions still require the user's explicit authorization.

## Acceptance

Run `doctor`, then `desktop_start`; obtain guest windows/screenshots through the plugin, execute a test and read back its result, confirm the host desktop is unchanged; after stopping, confirm the VM is still running. Only test disconnect/lock behavior on a dedicated test machine with no unsaved work.

Development so far had neither usable Hyper-V management permission nor configured VM credentials, so real Hyper-V logon/screenshot/input acceptance must still happen in the deployment environment. The connection-free ActiveX self-test and mocked transfer tests are not a substitute for real acceptance.
